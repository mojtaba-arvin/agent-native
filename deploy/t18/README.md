# T18 — PostgreSQL container pilot

This pilot runs the production T15 container image as a non-root service against a disposable PostgreSQL 16.4 instance. It is a deployment/integration smoke test, not a performance benchmark or a production-readiness claim.

## Run

Requirements: Docker Engine with Compose v2, Python 3.11+, and Git.

From the repository root:

```sh
T18_EVIDENCE_DIR=/tmp/agent-native-t18-evidence \
  bash deploy/t18/run-pilot.sh --acceptance
```

The runner invokes the complete T15 acceptance/reproducibility build from the current checkout, tags the verified image as `agent-native:t15`, and copies the T15 build/SBOM evidence into the T18 evidence bundle. It then creates a uniquely named Compose project, generates ephemeral PostgreSQL and token-signing secrets, waits for PostgreSQL and application readiness, and runs the black-box suite. It records sanitized deployment metadata, test output, application logs, an acceptance result, and operational findings. It never records secret values.

The runner always removes only its own Compose project and its disposable database volume. It does not touch unrelated Docker containers, volumes, images, or databases.

## Deployment configuration

- Application: `agent-native:t15`, root Dockerfile, UID/GID 65532.
- Database: immutable PostgreSQL 16.4 image digest.
- App ingress: host loopback only; container port 8080.
- Database ingress: Compose network only; no host port is published.
- Service manifests: read-only bind mount from `services/`.
- Root filesystem: read-only; `/tmp` is a bounded tmpfs; all Linux capabilities are dropped.
- Startup: application depends on PostgreSQL's health check and performs migrations before readiness.
- Secrets: ephemeral environment values generated by the runner; no secret is stored in the repository or evidence.

## Acceptance evidence

The black-box suite verifies:
- missing and invalid bearer tokens fail closed;
- readiness, liveness, and Prometheus metrics are served;
- Catalog create/read and atomic PostgreSQL audit/outbox/idempotency persistence;
- cross-tenant reads do not disclose another tenant's resource;
- created data survives application-container restart.

Evidence files are written under `T18_EVIDENCE_DIR`; the key sanitized configuration, acceptance result, findings, T15 provenance, and test/application logs are also rendered into the GitHub Actions step summary. The files are: `deployment.json`, `acceptance.json`, `acceptance.log`, `app.log`, `compose-ps.json`, `findings.md`, and `t15/` containing the reproducible T15 build evidence, SPDX SBOM, and CLI smoke output. Deployment metadata contains image IDs, source revision, exposed ports, and security settings, but never credentials.

## Operational findings

The pilot proves the packaged service can load the declarative service registry, connect to PostgreSQL, apply service migrations, authenticate signed capability tokens, and serve bounded HTTP requests while persisting data and audit/outbox records. The database remains private to the Compose network and the application binds only to host loopback.

## Limitations

This is a single-node disposable integration pilot. It does not prove high availability, backup/restore, failover, multi-node coordination, production secret rotation, external job-worker execution, event delivery, or the T02/T16 performance envelope. The current pilot exercises Catalog CRUD; queue and event handlers are not claimed as operationally backed by PostgreSQL.
