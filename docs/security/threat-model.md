# Initial Threat Model

Status: preliminary; must be validated and expanded before implementation.

## Assets to protect

- Application data and tenant boundaries.
- Credentials, API keys, signing keys, and deployment secrets.
- Production infrastructure and deployment authority.
- Source code, build artifacts, dependencies, and release integrity.
- Audit records and approval decisions.
- Availability, resource budgets, and service integrity.

## Trust boundaries

1. **Agent ↔ agent-facing interface:** agent output is untrusted input, even when generated by a trusted model.
2. **Agent interface ↔ framework control plane:** requests must be parsed, validated, authorized, and audited.
3. **Control plane ↔ execution environment:** build and test operations require isolation and resource limits.
4. **Application ↔ data and external services:** application permissions must be scoped and enforced independently of agent intent.
5. **Development ↔ production:** deployment and destructive operations require explicit policy and auditable authorization.
6. **Repository content ↔ agent context:** files, issues, dependencies, generated docs, and tool outputs may contain hostile instructions or misleading data.

## Threat scenarios

- Prompt injection in repository files, API responses, logs, issue text, or dependency documentation.
- Agent requests a tool action outside its assigned task or privilege scope.
- Secret leakage through model context, logs, traces, generated artifacts, or test output.
- Unsafe shell, code, migration, or plugin execution.
- Cross-tenant data access caused by missing or bypassed authorization checks.
- Malicious or compromised dependencies and build scripts.
- Resource exhaustion through unbounded loops, queries, jobs, or agent retries.
- Destructive migration or deployment without sufficient review.
- Forged or misleading verification results.
- Audit log tampering or missing attribution.

## Baseline security requirements

- Enforce authorization in trusted runtime code; never rely on model instructions as access control.
- Use least-privilege, short-lived, scoped capabilities.
- Keep secrets out of model context by default; expose secret references or brokered operations where possible.
- Isolate untrusted execution and enforce CPU, memory, process, filesystem, and network limits.
- Validate all structured inputs against versioned schemas.
- Require explicit approval for defined high-impact actions.
- Make operations idempotent or safely reject ambiguous retries.
- Record actor, capability, target, request, decision, result, and correlation identifier in audit events.
- Treat tool outputs and repository content as untrusted data.
- Provide safe cancellation, timeout, and recovery semantics.
- Protect build and release provenance.
- Test tenant isolation and authorization boundaries at the data and service layers.

## Security design questions

- What is the smallest capability model that is expressive enough for real tasks?
- How are capabilities attenuated when delegated to another agent or process?
- Which execution operations require a sandbox, and what isolation guarantees can be provided?
- How are approvals represented, expired, and bound to exact action parameters?
- How can a human independently verify an agent's claimed test and deployment results?
- How are audit events protected from application-level modification?
- What is the policy for network access during build, test, and runtime?

## Non-goal

The framework cannot guarantee that generated application code is secure merely by providing secure tools. Applications still require secure design, review, testing, dependency management, and operational controls.
